# План миграции на Spring Boot

## 1. Цель и границы миграции

Перевести приложение с Jakarta Servlet + самописного DI + Hibernate на Spring Boot.
Результат: запускаемое Spring Boot-приложение с PostgreSQL, Spring Data JPA,
REST-контроллерами, сервисным слоем, Spring Security и JWT, тестами, мониторингом,
Docker и CI.

Генератор DOCX (`ru.ecospas.word`) и существующая предметная модель сохраняются:
их нужно подключить к Spring, а не переписывать без необходимости.

## 2. Что уже есть

| Область | Состояние | Решение при миграции |
| --- | --- | --- |
| Сущности | 40+ JPA/Hibernate-сущностей в `domain.model`, связи и таблицы уже описаны | Сохранить аннотации, проверить схему и ограничения |
| Доступ к данным | `GenericHibernateRepository`, `HibernateUtil`, HQL | Заменить на Spring Data JPA-репозитории |
| Бизнес-логика | Сервисы в `domain.service` | Сделать Spring-бинами, добавить `@Transactional` на операции записи |
| HTTP | Сервлеты, `AuthFilter`, JSP и JavaScript | Перенести API в `@RestController`; переход JSP выполнять отдельно/постепенно |
| Авторизация | Сессия, роли `ADMIN` и `USER` | Заменить на stateless JWT, сохранить модель ролей |
| БД | PostgreSQL, Hibernate `hbm2ddl=update` | Управлять схемой через Flyway; отключить auto-DDL вне локальной разработки |
| Контейнер | Есть Dockerfile для WAR + внешнего Tomcat | Перейти на образ Spring Boot приложения; добавить Docker Compose |
| Тесты | Только устаревший шаблон JUnit 3 | Ввести JUnit 5, Mockito, Spring Boot Test и Testcontainers |
| CI/CD | Конфигурации нет | Добавить pipeline после стабилизации сборки |

### Выявленные расхождения в репозитории

- В README заявлен `docker-compose`, но compose-файла нет.
- Dockerfile собирает WAR для Tomcat 10.1; это не Spring Boot-развёртывание.
- В `pom.xml` нет Spring, JWT, Actuator и современных тестовых зависимостей.
- Пароль PostgreSQL задан как значение по умолчанию в коде. Его нужно убрать из
  исходников и передавать только через переменные окружения/секреты.

## 3. Целевая архитектура

```text
HTTP client
    -> Spring MVC controllers (/api/**)
    -> services (@Service, @Transactional)
    -> Spring Data JPA repositories
    -> PostgreSQL

Spring Security JWT filter -> SecurityContext -> controllers/services
Actuator -> health, metrics, info (в production доступ ограничен)
```

- Формат приложения: исполняемый Spring Boot JAR с embedded Tomcat.
- Базовый URL API: `/api`.
- DTO отделяют API от JPA-сущностей; сущности нельзя возвращать напрямую из
  контроллеров из-за ленивых связей и риска раскрытия полей, включая пароль.
- Ошибки возвращаются единообразно через `@RestControllerAdvice`.
- Токен содержит идентификатор пользователя и его роль; пароли хранятся только
  в виде BCrypt-хеша.

## 4. Последовательность работ

### Этап 0. Зафиксировать исходное состояние

1. Сделать резервную копию рабочей PostgreSQL-базы и проверить, что приложение
   собирается в текущем виде.
2. Составить таблицу соответствия: servlet URL -> будущий API endpoint -> метод
   и права доступа. Отдельно зафиксировать сценарии генерации и скачивания DOCX.
3. Выбрать способ перехода фронтенда: существующий JSP/JS временно обращается к
   новому API либо он заменяется отдельным клиентом. В рамках backend-миграции
   JSP не переписывать без отдельной задачи.

**Готово, когда:** есть дамп БД и таблица маршрутов; известны сценарии, которые
нельзя сломать.

### Этап 1. Создать каркас Spring Boot

1. Изменить `pom.xml`: Spring Boot parent/BOM, `spring-boot-starter-web`,
   `spring-boot-starter-data-jpa`, validation, security, actuator и test starter.
   Убрать JUnit 3 и дублирующие вручную подключённые зависимости Spring Boot.
2. Добавить `EcospasApplication` с `@SpringBootApplication` и profiles
   `local`, `test`, `prod`.
3. Вынести настройки в `application.yml` и profile-файлы. URL БД, логины,
   пароли и JWT secret получать из окружения; подготовить `.env.example` без
   реальных секретов.
4. Перенести инициализацию docx4j из `AppInitializer` в Spring-конфигурацию.

**Готово, когда:** `mvn test` и `mvn spring-boot:run` стартуют; `GET /actuator/health`
возвращает UP при доступной БД.

### Этап 2. Перенести БД и слой данных

1. Проверить все существующие `@Entity`, имена таблиц, связи, nullable/unique
   ограничения и индексы на копии реальной БД.
2. Добавить Flyway. Сформировать начальную миграцию из согласованной схемы, а
   не полагаться на `hibernate.hbm2ddl.auto=update`.
3. Создать типизированные `JpaRepository`-интерфейсы для `User`, `Organization`,
   `ObjectModel`, ASF и справочников; сложные HQL-запросы перенести в JPQL либо
   спецификации.
4. Удалить из runtime-пути `HibernateConfig`, `HibernateUtil`,
   `GenericHibernateRepository`, `Bootstrap`, `ApplicationContext`,
   `RepositoryContext` и `InternalServices` только после перевода их потребителей.

**Готово, когда:** приложение поднимает схему Flyway и читает/изменяет данные
через Spring Data JPA без ручного открытия Hibernate Session.

### Этап 3. Сервисы и REST API

1. Перевести существующие сервисы в `@Service`; операции изменения данных
   оформить `@Transactional`.
2. Ввести request/response DTO и Bean Validation (`@Valid`), маппинг DTO и
   обработчик ошибок.
3. Переносить сервлеты функциональными группами: авторизация, организации,
   объекты, ASF, справочники, загрузка изображений, генерация и скачивание DOCX.
4. Для файлов использовать `MultipartFile`; пути, лимиты и типы файлов вынести
   в конфигурацию. Для загрузки DOCX отдавать корректные
   `Content-Disposition` и `Content-Type`.
5. Проверить авторизацию на уровне ресурса: пользователь может работать только
   с закреплёнными за ним организациями, ADMIN — со всеми.

**Готово, когда:** каждый старый пользовательский сценарий имеет endpoint,
валидацию, единый формат ошибок и проверку прав.

### Этап 4. Spring Security и JWT

1. Добавить endpoint `POST /api/auth/login`, проверку пользователя через
   `UserDetailsService` и `PasswordEncoder(BCrypt)`; провести разовую миграцию
   старых паролей в хеши до включения нового входа.
2. Реализовать выпуск и проверку JWT, filter `OncePerRequestFilter`, stateless
   session policy и корректные ответы 401/403.
3. Описать правила доступа: публичны login и health; бизнес-API требует токен;
   административные операции требуют `ROLE_ADMIN`.
4. JWT secret, срок действия и CORS-конфигурацию хранить в переменных окружения.
   Не включать token/пароль в логи и репозиторий.

**Готово, когда:** вход выдаёт JWT, запрос без него получает 401, а USER не
может вызвать ADMIN-endpoint или получить чужую организацию.

### Этап 5. Тестирование

1. Unit-тесты JUnit 5 + Mockito: бизнес-правила, проверки доступа, маппинг,
   сервис генерации документа и JWT-компоненты.
2. Интеграционные тесты `@SpringBootTest`/`MockMvc`: login, права ролей,
   CRUD, валидация, загрузка файлов и выдача DOCX.
3. Для PostgreSQL использовать Testcontainers, не локальную разработческую БД.
   Проверять применение Flyway-миграций в тестовом контейнере.
4. Настроить отчёт о покрытии (JaCoCo) и минимальный порог только после появления
   репрезентативного набора тестов.

**Готово, когда:** тесты запускаются одной командой `mvn verify` и не зависят от
локально установленного PostgreSQL.

### Этап 6. Наблюдаемость и логирование

1. Настроить структурированные логи и уровни логирования по profiles; добавить
   request/correlation ID и логирование исключений без секретов.
2. Подключить Actuator: `health`, `info`, `metrics`, `prometheus` при наличии
   Prometheus. Не публиковать `env`, `configprops` и heapdump наружу.
3. Добавить readiness/liveness probes для контейнерного окружения.

**Готово, когда:** состояние приложения и БД наблюдаемы, а health endpoint
готов для оркестратора.

### Этап 7. Docker и CI/CD

1. Заменить Dockerfile на multi-stage сборку Spring Boot JAR, запускать под
   непривилегированным пользователем, добавить `.dockerignore`.
2. Добавить `compose.yaml` с PostgreSQL, volume, healthcheck и передачей
   конфигурации через `.env`; не встраивать пароли в образ.
3. Добавить CI (предпочтительно GitHub Actions после подтверждения площадки):
   checkout -> cache Maven -> `mvn verify` -> build image -> scan/push image.
4. Deployment вынести в отдельный job, запускать только из защищённой ветки/тега
   и передавать секреты через хранилище CI. Способ деплоя (Railway, VPS, registry)
   согласовать перед реализацией.

**Готово, когда:** чистый клон проекта собирается и тестируется в CI, а образ
запускается через Compose.

### Этап 8. Приёмка и очистка legacy

1. Пройти ручный smoke-test основных сценариев на копии production-данных.
2. Удалить сервлеты, `AuthFilter`, `web.xml`, самописный DI и legacy Hibernate
   только когда все маршруты переведены и покрыты тестами.
3. Обновить README: запуск, переменные окружения, API, миграции, тесты, Docker,
   мониторинг и rollback.

## 5. Порядок приоритета

1. Этапы 0–3: минимальный работающий Spring Boot backend.
2. Этапы 4–5: безопасность и доказательство корректности.
3. Этапы 6–7: бонусные требования и эксплуатационная готовность.
4. Этап 8: удаление legacy после успешной приёмки.

## 6. Важные решения до начала реализации

- CI-площадка и конкретный способ production-деплоя пока не определены, поэтому
  pipeline не стоит «додумывать» заранее.
- Нужен безопасный способ получить схему/дамп существующей PostgreSQL БД для
  первой Flyway-миграции.
- Если текущий JSP-интерфейс должен остаться без изменений, JWT придётся
  согласованно подключить к его JavaScript-клиенту. Альтернатива — временно
  оставить session-based UI, но это не выполнит требование stateless JWT для API.
